## 调研：TokenTracker 如何追踪 CodeBuddy token 用量

- 真正的取数方式 = **被动文件读取（passive reader）**，不是 hook 取数。
  - 源1：`~/.codebuddy/projects/<encoded-cwd>/<sessionId>.jsonl` 会话日志，只取 `type=="message" && role=="assistant"` 且带 `providerData.rawUsage` 的行。
  - 源2：IDE 扩展日志（CodeBuddy CN / CodeBuddyExtension 的 `codebuddy-extension-log` 与 `*.log`），解析 `[AgentReporter] Agent execution successful with usage:` 和 `[CraftInvokableAgent] Model prepared:`。
- 增量机制：`cursors.codebuddy.fileOffsets`（字节偏移 + inode）+ `seenIds` 复合 messageId 去重；30 分钟 UTC 分桶写入 `~/.tokentracker/queue.jsonl`。
- Token 换算（OpenAI 风格 prompt_tokens 含缓存）：input = prompt - cached；cached_input = cached；output = completion；reasoning_output = reasoning_tokens。成本只用 input+output+cached+cache_creation+reasoning 计算，不用 total_tokens。
- 成本：hy3 系列已在 `curated-overrides.json` 有定价（hy3-preview / hy3-preview-agent，腾讯 TokenHub 汇率换算），非 hy3 模型显示 $0。

## ⚠️ 代码矛盾（值得注意）
- README 支持表 + `status.js` 标注 CodeBuddy 用 "SessionEnd hook in ~/.codebuddy/settings.json"。
- `init.js` 确实会装该 hook（`upsertClaudeHook`，指向 `notify.cjs --source=codebuddy`）。
- 但 `sync.js:1448` 与 `rollout.js:6362` 注释明确写 "CodeBuddy ships NO hook system — passive scan only"，且 `parseCodebuddyIncremental` 完全从文件增量读取，不依赖 hook 取数。
- 结论：hook 装了但只是触发 sync 通知，数据来自被动扫描；README/status 的 "hook" 说法与 sync/rollout 注释不一致。

## 调研：Trae / Trae CN 能否用同样方法拿 token
- **Trae 已被 TokenTracker 支持**（source "trae" + "trae-solo"，IDE/Solo 两种变体），但**方法不是被动读本地文件，而是 API 拉取**。
- 链路：`trae-config.js` 从 `~/.../Trae/User/globalStorage/storage.json` 解密 OAuth token → `trae-sync.js` 调 `https://api-sg-central.trae.ai/trae/api/v1/pay/query_user_usage_group_by_session`（分页）→ 写入 `~/.tokentracker/trae-cache`（manifest + 各 session artifact）→ `rollout.js parseTraeIncremental` 从缓存读 `input/output/cache_read/cache_write_token` 入队。
- **为什么不能照搬 CodeBuddy 的被动文件法**：Trae（字节）不像 Claude Code fork 那样吐本地 per-message `rawUsage` JSONL，用量在服务端，只能走官方 API。
- **代价**：需登录凭据（auto-decrypt storage.json 或手动 login），非零配置；Trae 是 account-level 源（按账号聚合，非按本地项目文件）；成本 `$0`（curated 里 trae-auto / trae-unknown 全 0，厂商未公开按 token 计价）。
- **"Trae CN" 注意点**：Trae 集成只检测 app dir "Trae"(IDE) / "TRAE SOLO"(Solo)；"Trae CN" 字符串仅出现在 rollout.js 的多 IDE `ui_messages.json` 扫描（给 Kilo Code 等被动读取器用），Trae 自身追踪不识别 "Trae CN" 目录名 —— 若 CN 版装到不同 app dir 名可能漏检。

- 重新提取 queue.jsonl 中 grok-build 那条记录的 hour_start = `2026-07-20T08:30:00Z`（北京时间 2026-07-20 16:30），total_tokens=23325，conversation_count=1。

- 修正前一结论：grok-build 是约 35 分钟前的实时数据，非旧 session 残留；根因是兜底逻辑对部分 session 仍在触发（需查明为何该 session 的 signals 缺版本号，而非单纯"重跑覆盖"）。

## 根因定位：grok-build 来自"进行中 session"的时序漏读（2026-07-20 17:14）
- 遍历全部 10 个 grok session：6 个有 signals.json 的全是 grok-4.5（无缺失）；有 4 个目录无 signals.json。
- 其中 **"有 updates.jsonl 但无 signals.json"** 的 session 会被 rollout.js:12773 的 OR 条件纳入统计，模型因无 signals 兜底为 `grok-build`。
  - `E%3A%5CProjects%5CTokenTracker/019f7ecc-05eb-71a2-9775-0b330f823453`：updates.jsonl 138 行，mtime 2026-07-20 17:14:55（实时增长，仍在进行中），末行 `_meta.totalTokens=62313` → **即 queue 里那条 grok-build（16:30 桶 total=23325 是当时累积快照，后续已涨到 62313）**。
  - `E%3A%5CProjects%5Cnovel-writer/019f5936`：同为"有 updates 无 signals"，但末行是 rate_limit 的 turn_completed、`_meta` 无 totalTokens → token≈0 不入队，故 queue 仅 1 条 grok-build。
- **机制**：`signals.json` 在 SessionEnd 时才生成（含 primaryModelId）；`updates.jsonl` 是实时累积、仅含 `{timestamp,method,params{...,_meta:{totalTokens}}}`、**无 model 字段**。TokenTracker 模型只能从 signals.json 读，进行中 session 必有用量无 signals → 兜底 grok-build。
- 结论：这不是数据缺失，是"进行中 session 的同步时序"问题。session 结束后重跑 sync，signals.json 生成即纠正为 grok-4.5。修复建议：无 signals 时不要强行兜底 grok-build（会错算费用），改为留 unknown/待回填。
